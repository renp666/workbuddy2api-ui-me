## 〇、一句话结论

棱镜网关**已在生产运行**，同时长期承载「新增通道 / 单通道排错与修复 / 整体健康检查 / 实用性功能 / 统计功能」五类优化任务。因此运行的第一性要求是**任何时刻至少有一条通道对 agent 可用**；当前已有的别名候选链 + 探测结论 + 熔断器已覆盖「请求前选路」，但**缺请求内重试**，且冷却参数偏粗（固定 30min）。全网调研结论：agent2api 生态的薄翻译型项目普遍无网关层容错，可借鉴的是 LiteLLM（请求内 fallback）、Envoy outlier_detection（指数冷却）、CLIProxyAPI/ juhe-ai（多因子有界换号）。

## 一、生产环境任务体系与变更规则

### 1.1 任务类型（长期共存）

| 类型 | 说明 | 典型改动面 | 是否动生产数据面 |
|---|---|---|---|
| 新增通道 | 接入新上游（sidecar + console 分流 + 页签 + 探针） | `console/*.go`、`deploy/compose.<ch>.yml`、`console/web/*` | 是（新增出海口，不改既有） |
| 单通道排错/修复 | 某通道不可达、超时、鉴权失效、模型漂移 | 该通道 sidecar 或 console 分流代码 | 是 |
| 通道新增功能 | 给某通道加签到/账号/积分/用量等控制链路 | `console/<ch>control.go`、页签 | 视情况 |
| 整体通道健康检查 | 全通道体检 → 结果总结 → 修复 | 只读探测 + 文档 | **否**（零改数据面） |
| 实用性功能开发 | 路由、别名、模型开关、对话测试等 | `console/route.go`、前端 | 可能 |
| 统计功能开发 | 用量/错误/时延统计、报表 | `console/errors.go`、`usage_report.go` | 否（旁路观测） |

### 1.2 变更规则（已定）

1. **合流靠 console 代理层**：console 只做路径分流，不加载上游凭据；channel 能力一律留在各自 sidecar，不在网关重复实现供应商池。
2. **生产入口不变**：生产始终是 `docker compose up -d`（只读 `docker-compose.yml`）；新增/排错**不得**引入新的宿主启动脚本或必填密钥。
3. **改配置必须串行**：`enabled_models` / `routes.json` 整组落盘存在并发覆盖风险，所有自动改配置（熔断、自动切换）与管理页保存共用同一把锁。
4. **旁路重建连带**：旁路以 `network_mode: service:console` 绑定 console 容器 ID，**单独重建 console 会让全部旁路永久 Exited(255)**。重建 console 必须连带重建旁路（带 override 的 `docker compose up -d` 天然一并处理）。
5. **不触碰无关通道**：修 A 通道时，B/C/… 通道的容器、配置、凭据一律不动。
6. **留痕**：每次通道级改动在 `docs/superpowers/verification/` 留验证记录（含 image ID）；routes 变更先落 `routes.bak`。

## 二、生产改码的容错铁律（保活优先）

**前提（最高优先级）：改任何通道时，其余通道在改动的全过程中必须保持通畅，确保 agent 始终有 LLM 可用。**

### 2.1 保活分层

```text
agent 客户端
   │  （配置的别名：daily / fast / strong / max / free …
   ▼
棱镜网关 console ── 别名候选链（fallbacks）+ 探测结论 + 熔断器
   ├─ 通道 A（正在改）── 临时不可用/降权
   └─ 通道 B/C…（必须始终可达）← 保活对象
```

保活的实现依赖三层，任一层都不能在改动中被破坏：

| 层 | 机制 | 现状 |
|---|---|---|
| 1 别名候选链 | `fallbacks` + `strategy: health`，主目标挂自动落同梯队备用 | 已上线（`console/route.go`） |
| 2 探测结论 | `probe` band 0/1/3 + 30s 缓存；无结论时按链序 | 已上线（`console/probe.go`） |
| 3 熔断摘链 | 连续失败 ≥3 或 15min 错误率 >80% 自动摘链切备用，30min 冷却 | 已上线（`console/circuit.go`） |

### 2.2 改 A 通道时的强制动作

1. **改前**：确认至少一条**与 A 不同通道**的在用别名链路当前为绿（`GET /admin/health` 或页签通道状态），并记录基线。
2. **改中**：A 通道容器可停、可重建；**不得**重启 console 本体（除非连带旁路一起重建）。若必须重建 console，先确认 agent 侧至少有一条非 console 内生链路（即已起床的旁路 sidecar）可用。
3. **改后**：A 通道先手工探测 `POST /admin/probe` 确认真调用可用，再放回选路；确认别名链路已回到主目标。
4. **兜底**：任何时刻 agent 侧可临时切到 `gateway-auto`（全局自动选路）或另一条 `priority` 别名。

### 2.3 禁止事项

- 禁止在未确认备用链路健康的情况下重建 console 本体。
- 禁止把「同时改两个以上通道」当作常规操作（除整机冷启动重建）。
- 禁止为通过验证而重置工作区、清空 `runtime/` 或覆盖生产凭据。
- 禁止关闭同源/CSRF/会话归属/桥接认证等既有安全闸。

## 三、待拍板：测试 + 生产双环境并行方案

### 3.1 现状约束

- 单实例：project 默认名，console 只发布 `0.0.0.0:7863`，数据全在 `runtime/wb2api/`。
- `docker-compose.build.yaml`（源码构建 `:dev`）**与生产共享 `runtime/wb2api/`**，两者不可同时启动（AGENTS 硬约束）。
- 旁路 sidecar 依赖 console 的网络命名空间，无法脱离 console 单独存活。

### 3.2 三个候选方案

| 方案 | 做法 | 资源 | 能验证什么 | 风险/代价 |
|---|---|---|---|---|
| **A 同机第二套「演练环境」**（推荐） | 新增 `deploy/compose.lab.yml`：独立 project `prism-lab`、端口 `7864`、数据目录 `runtime/lab/`、镜像用独立标签 `:lab`（不复用 `:local`，避免与生产同标签） | 多 1×console + 1×core（约几百 MB）；按需再加单个被改通道的 sidecar | 路由/别名/熔断/健康/统计/前端**以及单通道真调用** | 需新增 1 个 overlay 文件；需注意 7864 不在 Hyper-V 保留区间 |
| **B 只读影子探测** | 不起第二套，只对生产 console 的 `/admin/*` 做只读体检与回归脚本 | 近零 | 只读结论（健康/错误/统计） | **不能**验证新代码，不满足「安心改代码」 |
| **C 单实例内开关灰度** | 同进程加 feature flag | 零 | 逻辑分支 | 生产进程内跑未验证代码，违背保活铁律，**不推荐** |

### 3.3 方案 A 落实步骤（待拍板后执行）

1. **新增 `deploy/compose.lab.yml`**（可选叠加层，不影响生产 `docker compose up -d`）：
   - `core` / `console`：`image: workbuddy2api-{core,console}:lab` + `pull_policy: never`；
   - `console` 宿主端口 `0.0.0.0:7864:7863`——只换宿主侧映射，容器内监听仍是镜像内置的 `:7863`
     （与 `WB2A_CORE_URL=http://core:7863` 自洽，不必改镜像 ENV；lab 与生产是两套 project，内网端口不冲突）；
   - runtime 挂载用 `!override` 整体替换为 `runtime/lab/`（auths/data/keys/console 各自独立）——
     普通列表按容器内 target 合并会把基类的 `./runtime/wb2api/*` 保留下来，必须显式覆盖；
   - 默认**只含 core+console**，不含任何旁路 overlay。
2. **构建入口**：`scripts/local-release.sh` 增加可选 `--tag SUFFIX`，产出 `:lab` 标签，并跳过
   `:local`/`:local-prev` 滚动与生产重启；生产仍走默认（不带 `--tag`）。
3. **启动命令**（只影响演练，不碰生产）：
   ```bash
   docker compose -p prism-lab -f docker-compose.yml -f deploy/compose.lab.yml up -d
   ```
4. **单通道验证**：需要验证某通道时，临时把该通道 overlay 以 `-f deploy/compose.<ch>.yml` 叠加进 lab，**且只在 lab 使用该通道的独立凭据**；验证完即停 lab，不影响生产旁路。
5. **升级路径**：lab 验证通过 → `docker compose up -d`（生产）滚动到 `:local` 新镜像；失败则 lab 停止，生产零影响。
6. **资源与灵活点**：lab 可随时 `docker compose -p prism-lab down`；数据目录独立，可反复重置；`WB2A_AUTOCLAW_*` 等密钥为 lab 专属。

### 3.4 需注意的坑（实施时写进验证记录）

- 端口 7864 需先确认不在 `netsh interface ipv4 show excludedportrange protocol=tcp` 的 Hyper-V 动态区间内（7863 曾因此被吞）。
- lab 不得复用 `runtime/wb2api/`，否则与生产/ build 入口互相污染。
- lab 用 `-f` 叠加（不是 `include`），相对路径按 project 目录解析：实测 `./runtime/lab/keys` 落在 `<root>/runtime/lab/keys` 而不是 `deploy/runtime/lab/keys`——与 `include` 的坑正好相反，别照搬 `project_directory` 处理。

### 3.5 拍板结论（2026-10-18）

- **采用方案 A**：同机第二套演练环境（project `prism-lab`、端口 7864、数据目录 `runtime/lab/`、镜像标签 `:lab`）。
- lab 初始**只含 core+console**（省资源）；需要验证某通道时临时叠加该通道 overlay。
- `:lab` 标签产出方式实施时定（优先复用 `local-release.sh` 扩参数，不新建第二套构建逻辑）。

## 四、问题一 —— 常见 LLM 错误归纳与自动冷却

### 4.1 现状（已具备）

| 能力 | 现状 | 文件 |
|---|---|---|
| 错误事件账本 | `errors-YYYYMMDD.jsonl` 按天轮转、保留 30 天、脱敏 | `console/errors.go` |
| 错误归类 | `failureCategory`：`auth` / `model_error` / `rate_limit` / `timeout` / `upstream_error` / `pin` / `error` | `console/probe.go:388` |
| 内存窗口聚合 | 15m/1h/24h 按 (通道,模型,类别)；`/admin/errors` 输出错误率/Top榜/时延/`r429_daily` | `console/errors.go` |
| P1 告警 | 别名 15min 错误率 >50%（样本≥5）、任一 pin 错误；30min 抑制 | `console/errors.go` |
| 熔断降级 | 连续失败 ≥3 **或** 15min 错误率 >80%（样本≥5）→ 摘链切备用；**固定 30min 冷却**后恢复；3-strong 受保护 | `console/circuit.go` |

### 4.2 常见错误归纳（口径来自 `failureCategory` + 上游实证）

| category | 触发 | 是否适合「冷却该链路」 | 处置建议 |
|---|---|---|---|
| `rate_limit` (429) | 上游限流/配额耗尽 | **是**，应按 `retry-after` 定时冷却 | 见 4.3 |
| `upstream_error` (5xx) | 上游故障 | **是**，指数冷却 | 见 4.3 |
| `timeout` (408/504) | 上游慢/卡 | 是（但 qoder 类慢通道需单独放宽超时） | 冷却 + 按通道调 `probeChannelTimeouts` |
| `auth` (401/403) | 凭据失效/被风控 | 不是「临时冷却」，需人工重登 | 停止自动恢复，直接 P1 找人 |
| `model_error` (404) | 模型下架/名字错 | 不是冷却，是配置漂移 | 走「目录漂移审计」，修正名字 |
| `pin` | core 严格 pin 账号被锁 | **跳过熔断**（既有口径）；已在 circuit.go 中排除 | P1 告警 + 对照 `corePinHint` |
| `error` | 未归类 | 观察 | 聚类后补口径 |

### 4.3 冷却机制升级建议（现状偏粗：30min 固定、80% 窗口偏长）

| 改造点 | 借鉴 | 具体建议 |
|---|---|---|
| 冷却指数化 | Envoy `outlier_detection`（`base_ejection_time` × 连续弹出次数，封顶） | 基底 30–60s × 连续摘链次数，封顶 10–30min |
| 半开探测恢复 | agenthood（到期前轻量 probe） | 冷却到期前 30s 用现有 `band` 发 1 次轻量探测：成功即回池，失败延长冷却 |
| 429 感知冷却 | 厂商 `Retry-After` / `x-ratelimit-*` | 有头则按头定时；无头则指数退避 + 抖动（智谱 429：`1302`/`1305`，按**并发在途**维度） |
| 触发阈值校准 | LiteLLM `allowed_fails:3`、Envoy `consecutive_5xx:5`、Higress 失败率 50% | 窗口错误率阈值由 80% 下调到 ~50%，窗口由 15min 缩短到 ~60s（更快识别） |
| 分类冷却策略 | — | `rate_limit`/`upstream_error`/`timeout` 走自动冷却；`auth`/`model_error`/`pin` 不自动恢复、只告警 |

> 冷却参数为一次性拍板项，建议先按「指数冷却 + 半开探测 + 429 感知」实现，参数集中成常量便于后续调。

### 4.4 拍板结论（2026-10-18）

- **与请求内重试合并为同一批**实施（§五 5.3-1 + §四 4.3）。
- 冷却升级为「指数 + 半开 + 429 感知」；触发阈值由「15min >80%」下调为「60s >50%」（业界口径）。
- `Retry-After` 接入按「有头用头、无头退避+抖动」实现；实施前先实测各上游是否回该头。

## 五、问题二 —— agent2api 自动容错切换调研

### 5.1 调研结论（附不确定性）

**「agent2api 生态普遍缺少网关层自动容错」只对一半成立：**

- **薄翻译型**（把某客户端/官网接口反代成 OpenAI 兼容）：如 cursor2api / gemini-web2api / copilot-proxy-api / zcode-proxy 一类，**只做协议转换，普遍无多上游容错**。
- **已实现容错的成熟两类**：
  - **CLIProxyAPI**（Go，账号/Provider 级）：三层调度器，多账号负载均衡 + 故障转移 + 冷却队列（`cooldownQueue` + `nextRetryAt`），轮询策略 `round-robin` / `fill-first` / `weighted-round-robin`。
  - **juhe-ai**（Go）：12 类状态多因子排序 + **有界换号**（以「是否已交付可见输出」为语义边界）+ 探针治愈。

**真正的缺口**：即使上述项目，也多在**账号维度**而非**跨通道/跨模型的请求内重试**。这正是棱镜「只靠 agent 记忆切换」的根因——网关层没有同请求换链能力。

**对照论据**：Claude Code 自带 `fallback-model`，但**仅在该客户端内生效，换客户端即失效**；pi 亦同。故「网关层做」才能通用。

> 不确定性（必须如实标注）：GitHub 直连抓取受限，多处仓库页（含 `aimod-cc/agent2api`、本项目血缘仓）**未取到，星标/许可证/更新时间未核实，不给数字**；CLIProxyAPI 星标有两个时点（24K/38K，非同一时间），仅作区间参考；`one-switch`、`dsh-*`、`agenthood` 仅见零散片段，主体未核实；「agent2api」作为通名的精确定义未找到。

### 5.2 可借鉴清单

**可直接借鉴**

| 机制 | 出处 | 用途 |
|---|---|---|
| 请求内重试 + fallback 列表 | LiteLLM `num_retries`(默认3) → `fallbacks`（同请求内逐候选） | **补上棱镜缺失的「请求内重试」** |
| 请求内候选循环 + 分类重试 | one-switch（网络/超时/408/429/5xx 换候选，其他 4xx 直接返回） | 重试错误分类口径 |
| 归因响应头 | Cloudflare AI Gateway（`cf-aig-max-attempts`≤5、`retry-delay`≤60s、backoff、timeout） | 重试参数与响应头通报 |
| 指数冷却 + 半开 | Envoy `outlier_detection`（`consecutive_5xx:5`、`base_ejection_time`×次数、封顶） | 替换固定 30min 冷却 |
| 冷却到期前探测 | agenthood（到期前 30s 轻量 probe） | 半开恢复 |
| 冷却递增 | OpenClaw（30s→1m→5m 封顶，失败窗口结束即重置） | 冷却阶梯 |
| 熔断参数参考 | dsh-model-failover（模型阈值2/冷却60s；平台阈值2/冷却120s） | 双层阈值参考 |
| 智能选路策略 | LiteLLM `routing_strategy`（least-busy / latency-based / usage-based） | 替换简单轮询 |
| 故障窗口加权 | OpenRouter（优先 30s 内无故障 provider） | 选路第二输入 |
| 多因子有界换号 | juhe-ai（12 类状态排序，有可见输出即不再换） | 最接近「智能切换」 |
| 连续失败自动禁用 + 自动恢复 | new-api / one-api（渠道 Priority/Weight、失败自动禁用） | 与现有熔断同构，参数可参考 |

**需改造**：Portkey（`fallback/loadbalance` 配置模型重）、Higress AI 代理（`maxRetries` 默认1、被动健康检查失败率 50% 摘除、令牌降级）、one-api 按错误率自动禁用（`METRIC` 默认关闭）。

**不适用**：Anthropic 服务端 refusal fallback（平台侧行为、不可配）、纯价格优化路由（通道成本≈0，价格权重无意义）。

### 5.3 给棱镜网关的改造建议（均为网关层，增量最小化）

| # | 建议 | 借鉴 | 解决 |
|---|---|---|---|
| 1 | **请求内重试**（最高优先）：把现有候选链从「请求前选路」扩展为「同请求内逐候选执行」；主通道 5xx/429 后立即换下一候选 | LiteLLM `fallbacks` | 缺请求内重试；agent 无感 |
| 2 | **冷却指数化**：30min 固定 → 基底 30–60s × 连续摘链次数，封顶 15min | Envoy | 冷却不区分故障类型与频次 |
| 3 | **半开探测**：冷却到期前 30s 用现有 probe band 发轻量探测 | agenthood | 恢复过早/过晚 |
| 4 | **429 感知冷却**：读 `Retry-After`/`x-ratelimit-reset-*` 定时该通道冷却；智谱按并发维度退避 | 厂商规律 | 限流场景冷却无据 |
| 5 | **智能选路**：用 least-busy / latency-based 替换/叠加现有 band 排序 | LiteLLM / OpenRouter | 选路不够智能 |
| 6 | **归因响应头**：重试/切换后回传 `X-Routed-Via` / `X-Fallback-Attempts` / `X-Prism-Target-Index` | Cloudflare / 现有 `prismHeaderWriter` | 排障可追溯 |

> 现有 `prismHeaderWriter` 已回传 `X-Prism-Routed-Model/-Channel/-Reason/-Fallback/-Target-Index`，第 6 条主要是补「重试次数」语义。

### 5.4 拍板结论（2026-10-18）

- **优先级 1（请求内重试）+ 2/3（冷却指数化 + 半开）合并为一批**实施。
- 5/6（智能选路、归因响应头）放后续批次。
- 请求内重试的**流式、模型与会话边界**按用户口径细化（见 §八）。

## 八、请求内重试设计原则（2026-10-18 用户口径）

用户对 §五 5.3-1 的边界给定三条口径，作为实施的设计约束：

1. **按模型类型切换，优先「同名模型跨通道」**
   - 例：`trae-<model>` 失败时，切到 WorkBuddy（core）上**同名**的那个模型，而非语义不同的另一个模型。
   - 好处：agent 侧配置与提示词语义不变；同名映射可预先登记成对照表（trae ↔ core ↔ …）。
   - 载体：复用现有别名候选链，但候选链**按「同名模型」组织**（每个候选标明其对应上游的原生模型名）。
2. **同一会话不随便改模型（模型粘性）**
   - 同一 conversation/session 内恒定模型优先；**仅在主链路确定失败时**才切同名模型的另一通道。
   - 服务端不做「按会话强制重发上下文」的动作；失败切链要留痕（响应头 + 事件账本），便于区分「真实故障」与「抖动误切」。
   - 参考做法：LiteLLM `model_group`（同名模型跨 deployment）、OpenRouter provider 优先级 + 故障窗口。
3. **省 token**
   - 优先复用 prompt cache（同会话粘同一上游、或同名模型共享前缀）；避免把整段上下文重发到全新上游造成重复计费/重复推理。
   - 重试只在**首字节写出前**发生；一旦开始输出即不再换链重来（避免半截响应 + 重复计费）。
4. **参考开源实现**
   - 实施前先落一份「参考实现对照」（LiteLLM `fallbacks`/`num_retries`/`cooldown_handlers`、one-api/new-api 渠道重试与自动禁用、CLIProxyAPI 冷却队列），取其可用部分并对齐代码位置。

> 该口径把原设计里「换别的模型兜底」收敛为「换**同名模型的另一通道**兜底」：更保守、更省 token、对会话更友好。全局兜底 `gateway-auto` 不变。

### 9.2 与棱镜口径的映射（可直接照搬）

| 棱镜口径 | 现成语义 | 落点 |
|---|---|---|
| ①同名模型跨通道 | LiteLLM `model_group`（同 `model_name` 多 deployment）/ OpenRouter provider 层 | 别名候选链按「同名模型」组织，每候选标注其上游原生模型名 |
| ②同一会话不随便改模型 | new-api channel affinity + CLIProxyAPI `session-affinity` | 会话粘性优先，**仅在粘性链路确定失败时**才切同名模型的另一通道；切后跳过常规重试以免破坏亲和 |
| ③省 token | LiteLLM prompt caching 结论 | **关键是不换成不同模型名**——跨厂商 cache 换上游即失效，但回切同名模型缓存仍在；重试限首字节前，避免重发整段上下文 |
| 重试/回退分层 | LiteLLM retry vs fallback | retry 留在同名模型内换通道；耗尽才 fallback 到别组（或 `gateway-auto`）；失败候选加入本次排除集 |
| 冷却准入 | LiteLLM `_is_cooldown_required` | 429/5xx 冷却；4xx（含 auth/model_error）不冷却、只告警 |

### 9.3 重要修正（与 §4.3 的差异）

- **LLM 网关主流冷却是「固定窗口」而非指数**（LiteLLM `cooldown_time`、CLIProxyAPI `transient-error-cooldown-seconds`）；**未见成熟的「指数退避 + 半开熔断」实现**。故 §4.3 的「指数 + 半开」属**自研增强**，不是照搬。建议实施顺序：先做**固定窗口 + 首字节前请求内重试**拿到稳收益，再把「指数 + 半开」作为增量参数化上线。
- 口径 1/2/3 **在开源界有明确先例**，不是孤例，实施风险可控。
