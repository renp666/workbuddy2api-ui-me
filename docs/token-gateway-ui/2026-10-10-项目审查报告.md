## 二、缺陷清单

### A. 安全性

#### A1【高】管理密钥以明文写入容器日志

`console/main.go:198`

```go
log.Printf("[console] 管理密钥（仅交给管理员）: %s", cfg.AdminKey)
```

实测（值已脱敏，仅验证形态）：

```
2026/10/10 12:09:50 [console] 管理密钥（仅交给管理员）: [REDACTED]
2026/10/10 15:07:35 [console] 管理密钥（仅交给管理员）: [REDACTED]
```

每次启动都打印一次，`docker logs` 会长期保留。任何能读到容器日志的角色（`docker logs` 权限、日志采集器、CI 归档、崩溃转储）即取得管理员凭据 —— 而管理面本身正是靠这把密钥鉴权。

**建议**：只在密钥由本进程自动生成（非外部注入）时打印一次，或改为写入仅 root 可读的文件 / 打印指纹前缀（如 `sha256` 前 8 位）供比对，不打印全量。

#### A2【中】明文 HTTP 非回环监听（项目已知并自报警告）

`console/main.go:179` 有内置告警，启动时也会打印。属于**已知设计取舍**，非未知漏洞；但既然 `main.go` 已能识别该状态，建议升级为启动即拒绝（除非显式设置 `WB2A_ALLOW_INSECURE=1`），避免误暴露。

#### A3【低】DESIGN.md 记录的「已删除」令牌易被误读为漂移

`--faint` / `--shadow-sm` / `--shadow-lg` / `--prism-btn` 在 `DESIGN.md` 出现（各 1–2 次），但 `style.css` 中为 0 次。经核对上下文（`DESIGN.md:165`、`:255`、`:268`），这些**正是文档明文标注为"已删除"的旧令牌**，不是漏实现。属文档叙述方式问题，非代码缺陷。

### B. 代码缺陷

#### B1 已核验为**通过**：`/admin/tasks/{id}/runs` 可达

曾疑为"路由表与前端不一致"，实测**证伪**：前端 helper `api()`（`console/web/app.js:42`）内部做 `fetch('/admin/' + path, …)` 统一补前缀，因此 `app.js:980` 的 `jsonAPI('tasks/'+taskID+'/runs')` 最终请求 `/admin/tasks/<id>/runs` —— 与 `console/server.go:366` 注册的 `POST /admin/tasks/{id}/runs` **完全一致**。

进一步复核：84 条 `/admin/*` 注册路由中，**绝大多数**能在前端找到调用点；仅 3 条例外（见 E2），且那 3 条属"后端有、UI 无入口"而非路由错配。

**结论：该路由本身无缺陷。** 教训 —— 判断"路由不一致"必须先把 helper 的前缀拼接规则读透，否则会把正确的间接调用误判为缺陷。

#### B2【低】`zcodeClient` 无超时 —— 经核对为**有意设计**，但注释未标注风险上限

`console/server.go:99-101` 明确注释："It has no overall timeout so slow core model probes keep the same semantics as the plain proxy path."，且其 `CheckRedirect` 已设为 `ErrUseLastResponse`（禁止跟随跳转）。

无超时意味着上游挂死时该请求会长期占用 goroutine/连接。**建议**：保留语义的同时加一个**上限**（如 10 min 的 `Timeout` 或 `context` 兜底），既不改慢探测语义，又能回收僵死连接。

### E. 冗余功能

#### E1【低】`style.css:104-110` 的 `--ch-lit` 赋值链未被 `var()` 消费

`.ch-<通道>` 规则各赋值 `--ch-lit`，但全仓（`style.css` / `app.js` / `index.html`）**无任何 `var(--ch-lit)` 消费点**（实测 consumers = 0）。注释称其用于暗底文字色，实际无消费者 → 7 行赋值属冗余。

**注意**：`.ch-*` 上的 `--ch` / `--ch-ink` / `--ch-wash` 仍在用，**只能删 `--ch-lit` 这一段**，不要整块删。

#### E2【中】3 个已注册且处理器完整的 `/admin/*` 端点，前端 0 调用点（后端保留但无入口）

全仓扫描（`grep -rnI`，排除 `.git`/`node_modules`/`runtime`/`.build`）结果：以下 3 个路径**除注册行外，全仓无任何其它引用** ——

| 端点 | 注册 | 处理器 | 前端调用点 |
| --- | --- | --- | --- |
| `POST /admin/trae/login/cancel` | `server.go:301` | `trae.go:435 adminTraeLoginCancel` | **0** |
| `GET /admin/trae/accounts/json` | `server.go:306` | `trae.go:526 adminTraeAccountJSON` | **0** |
| `GET /admin/raccoon/usage` | `server.go:327` | `raccooncontrol.go:195 adminRaccoonUsage` | **0** |

对照：`trae/usage`（`app.js:3140`）、`raccoon/credits`（`app.js:3300`）、`autoclaw/credits/refresh`（`app.js:2789`）均有真实调用点 —— 说明同类通道端点**通常会**被前端接上，这 3 条属漏接。

**影响**：三条路径都由 `withAdmin` 保护，**不构成安全暴露**；但它们是"后端已实现、UI 无入口"的悬空能力 —— 要么补 UI 入口，要么确认废弃后摘除注册，避免路由表持续膨胀。

**注意**：`trae.go:434` 与 `:525` 的注释显示这两条是对 sidecar（`/admin/api/login/cancel`、`.../json`）的转发。若 sidecar 仍在提供该能力，则**属功能缺口（UI 未接）而非死代码** —— 建议优先补齐入口而非删除。

## 三、总体结论

**质量水位：良好。** 三套工具链检查全绿、测试密度高、安全面（CSP / Cookie / 限流 / 同源 / XFF / 凭据入库状态）经实测**基本完备**。

**真正需要动手的**：

1. **A1（高）**：`main.go:198` 明文打印管理密钥 —— 建议立即收敛打印条件。
2. **E2（中）**：3 个"后端已实现、UI 无入口"的端点（`trae/login/cancel`、`trae/accounts/json`、`raccoon/usage`）—— 建议先确认 sidecar 是否仍提供该能力，再决定**补 UI 入口**（功能缺口）还是**摘除注册**（冗余）。
3. **E1（低）+ D1（低）**：`--ch-lit` 无消费者的赋值链、3 个无 CSS 规则的类名 —— 清理即可，风险极低。

**一条待定**：B2（`zcodeClient` 有意无超时，建议加上限）。

**重要提醒**：本次审查中，早期基于朴素文本匹配得出的"死 CSS / 死端点"结论**绝大多数是假阳性**（动态构造类名、测试断言的类名、文档已声明的删除项）。报告 D2 表已逐条列出证伪证据 —— **修复前请勿按"死 CSS"清单批量删除**，否则会删掉在用的样式。
