# Qoder 通道「模型无法使用」排查报告

- 日期：2026-10-13
- 范围：棱镜网关（workbuddy2api-ui-me）Qoder 通道，只读排查 + 联网对照上游代码源
- 结论一句话：**qoder-proxy 本体完全正常（26/26 模型可用）；用户看到的「无法使用」由两个 console 侧的暴露/别名机制造成，且其中一个是本仓自加的发布白名单——不是 Qoder 上游故障。**
- 证据基线：本报告所有结论均由实测命令产出，命令与原始输出附在文末「附录 A」。

---

## 一、问题定位：用户侧到底是怎么失败的

用户在 console / 客户端里「选 qoder 模型 → 报错」，实际有三条互不相同的失败路径，之前被混在一起当成一个问题：

| # | 用户操作 | 实际返回 | 真实成因 | 是否 Qoder 的错 |
|---|---------|---------|---------|----------------|
| 1 | 在 `/v1/models` 里找不到 qoder 模型（除 1 个外） | 列表里 qoder 只有 1 条 | console 的**发布白名单**只启用了 `qoder-qwen3.8-flash` | ❌ 本仓机制 |
| 2 | 直接写裸模型名 `qwen3.8-flash` / `qwen3.8-max` / `kimi-k2.7-code` | `pinned_account_unavailable`（「该平台已人工锁定到指定账号…」） | 裸名**不带 `qoder-` 前缀**，不匹配 qoder 分流，落到 **core 通道**；core 该平台被人工 pin 且锁定账号不可用 | ❌ core 的 pin 机制 |
| 3 | 用别名 `4-max-v1` | **正常返回** | 别名→`qoder-qwen3.8-flash`，分流正确 | — 无故障 |

关键实测对照（同一时刻、同一网关）：

```
qwen3.8-flash      → pinned_account_unavailable     （裸名落 core）
qwen3.8-max        → pinned_account_unavailable     （裸名落 core）
kimi-k2.7-code     → pinned_account_unavailable     （裸名落 core）
qoder              → pinned_account_unavailable     （裸名落 core）
deepseek-v4-pro    → OK served=deepseek-v4-pro      （core 自己的模型，正常）
minimax-m3         → OK served=minimax-m3           （core 自己的模型，正常）

qoder-qwen3.8-flash → OK served=qwen3.8-flash       （带前缀，分流到 qoder，正常）
qoder-qwen3.8-max   → OK served=qwen3.8-max         （带前缀，正常）
4-max-v1            → OK served=qwen3.8-flash ×3/3  （别名，正常且稳定）
```

**这解释了「qoder 模型无法使用」的全部现象**：qoder 通道本身没有坏，坏的是用户输入的名字没有命中 `qoder-` 前缀分流，于是被当成 core 模型送进了 core 的账号锁定流程，而 core 那个平台恰好被人工 pin 到某个当前不可用的账号，于是报 `pinned_account_unavailable`——这个错误信息完全没有提到 Qoder，极具误导性。

## 三、根因一（主因）：console 发布白名单只放行了 1 个 qoder 模型

### 机制

console 的公共 `/v1/models` 走**启用表白名单**，只有管理员显式启用的直名模型才对外公布：

- `console/credits.go` → `modelPublished()`：`enabled, has := h.routes.modelOverride(model); return has && enabled`
- `console/zcode.go` → `mergedModels()`：逐条 `if !h.modelPublished(entry.ID) { continue }`

即「**配置了哪些就开放哪些**」——未配置/未启用的直名**不公布**，但**调用出口不拦**（`modelGate` 统一放行）。

### 实测状态

`runtime/wb2api/console/routes.json`：

```json
"enabled_models":  ["qoder-qwen3.8-flash", "autoclaw-cn:glm-5.3-flash", "global:deepseek-v4.1-flash"]
"disabled_models": ["global:hy4-preview-f", "cn:deepseek-v4-pro", "cn:glm-5.2",
                    "cn:hy3", "global:hy3", "global:kimi-k3"]
```

公共 `/v1/models` 实测：**总公布 16 条，其中 qoder 仅 1 条** = `qoder-qwen3.8-flash`。
而 qoder-proxy 实际广播 **26 个模型**。

### 归因：这是本仓自加机制，非上游

```
$ git log --oneline -S "enabled_models" -- console/
f8fed97 feat(console): 模型积分消耗开关（隐藏+拒绝、倍率倒序、人工覆盖落盘）
409997b 模型开关改双轨：调用统一对外开放，公布走启用表白名单
```

上游 `qoder-proxy` 1.6.0 的 `/v1/models` 是**全量返回**（26 条），console 在合并时用白名单把其中 25 条过滤掉了。

### 影响

用户在 console 模型列表 / `/v1/models` / 任何 `discover_models` 的客户端里**只能看到一个 qoder 模型**，自然认为「qoder 通道的模型用不了」。这是**最直接的用户可见症状**。

## 四、根因二：裸模型名不匹配前缀分流，被 core 的 pin 机制接住

### 机制

`console/zcode.go` → `publicRouter()` 按**模型名前缀**分流：

```
zcode-*    → zcode-proxy
qoder-*    → qoder-proxy      ← 必须带 qoder- 前缀
opencode-* → opencode sidecar
autoclaw-* → autoclaw2api
trae-*     → trae2api
raccoon-*  → raccoon2api
其它一切   → core
```

`qoder` 前缀是**硬约束**，另有一处显式报错印证：

```
POST /admin/qoder/chat  model=qoder
→ {"error":"Qoder 测试仅支持 qoder- 前缀模型"}
```

### 用户为什么会写裸名

qoder-proxy 自己的 `/v1/models` 返回的是**裸 id**（`qwen3.8-flash`、`kimi-k3`…）；用户从 Qoder 官方文档、CLI `--list-models`、或任何非 console 来源看到的名字都是裸名。写进 console 时前缀缺失 → 不匹配 → 落 core。

### 落 core 后为何报 pin 错误

`extensions/internal/pin/pin.go` 的账号 pinning：core 的某个平台被人工锁定到指定账号，且「严格锁定下不会自动切换其他账号」。锁定账号当前不可用 → `pinned_account_unavailable`。

**这是 core 的状态，与 Qoder 无关**，但错误信息不提 Qoder，导致排查方向被带偏。

## 五、根因三（次要，潜在）：已下架/改名模型静默降级为同名旧模型

上游 CHANGELOG 1.6.0 明写：

> Removed `qwen3.6-flash`… Requests for removed model IDs **fall back to `auto`**.
> Renamed: `qwen3.8-max-preview` → `qwen3.8-max`, `glm-5.2` → `glm-5.3`, `minimax-m2.7` → `minimax-m3`.

实测：请求已下架 id **不报错**，而是静默返回：

```

qoder-glm-5.2              → OK served=glm-5.2              ← 已改名，未报错
qoder-qwen3.8-max-preview  → OK served=qwen3.8-max-preview  ← 已改名，未报错
qoder-minimax-m2.7         → OK served=minimax-m2.7         ← 已改名，未报错

```

（注：console 的 26 模型清单里**不含**这些旧 id，所以只在直连 qoder-proxy 或白名单手工加错名时才会踩到。属于「防呆缺失」而非当前故障。）

## 六、上游对照：本仓 vs 上游的差异

| 维度 | 上游 qoder-proxy 1.6.0 | 本仓（workbuddy2api-ui-me console） |
|------|----------------------|-----------------------------------|
| 模型目录 | `/v1/models` 全量 26 条 | 合并后按白名单过滤，对外 1 条 qoder |
| 模型名 | 裸 id（`qwen3.8-flash`） | 对外强制 `qoder-` 前缀，调用时剥前缀 |
| 鉴权 | `PROXY_API_KEY`（可选） | console 统一 key + admin key，qoder 走内部 key |
| 登录 | `qodercli login` / `QODERCN_PERSONAL_ACCESS_TOKEN` | `qoder-login-ctl.cjs` + `runtime/qoder/.auth/` |
| 工具 | 1.6.0 起默认禁用 CLI 内置工具（`--tools=`），避免 agent 循环把 chat 拖成分钟级空响应 | 沿用，另有 `qoder-relax-token-guard.cjs`、`qoder-fix-e2big-argv.cjs` 两个本仓补丁 |
| 版本锚定 | — | `git clone --depth 1`（**未 pin tag/commit**） |

**上游 1.6.0 已修掉的两个已知坑**（与本仓症状高度相关，值得核对是否已受益）：
1. **CLI 内置工具默认禁用**——否则普通 chat 会变成 proxy 目录里的多轮文件/shell 循环，在 agent 客户端表现为**空响应**（"No response requested."）或 `upstream_timeout`。同 prompt 延迟从 ~220s 降到 ~3s。
2. **stdio 管道悬挂致请求永不结束**——CLI 退出但子进程继承 stdout 时 `close` 不触发，promise 永不 settle，连超时 kill 都杀不掉。

本仓跑的就是 1.6.0，两项修复已在位。

## 七、修复与优化方案

### P0 — 让用户能正常用到 qoder 模型（二选一或并用）

**方案 A（推荐，改配置不改代码）：扩充发布白名单**

把需要开放的 qoder 模型加进 `enabled_models`。当前 26 个可用，建议至少开放常用的：

```
qoder-qwen3.8-flash           （已在白名单）
qoder-qwen3.8-max             + effort-low/medium/high/max
qoder-qwen3.7-max             + effort-low/medium/high/max
qoder-kimi-k3
qoder-glm-5.3 / qoder-glm-5.3-flash
qoder-deepseek-v4-pro / qoder-deepseek-v4-flash
qoder-minimax-m3
qoder-ultimate / performance / efficient / cantus
```

落盘方式：控制台模型列表逐条点「启用」，或直接改 `runtime/wb2api/console/routes.json` 的 `enabled_models` 后重启 console。
> 注意：`enabled_models` 是**整组落盘**（`saveFile`），并发改需串行，避免互相覆盖。

**方案 B（治本，改代码）：qoder 通道改为「按通道整体公布」**

`modelPublished` 目前对**直名**要求显式启用。可对 qoder 这类「目录由上游决定、且已登录可用」的通道放宽为：**通道可达即整体公布其目录**，与 zcode 的 `zcodeEntitled` 语义对齐（后者本就是按权益过滤后整体放行）。

建议在 `mergedModels()` 里为 qoder 引入与 zcode 平行的 entitlement 概念：qoder-proxy `/v1/models` 返回什么就公布什么（去重后加前缀），不再逐条查 `enabled_models`。**保留 `modelGate` 不拦**，管理员仍可用禁用表单独下架某个模型。

### P1 — 消除裸名落 core 的误导

**方案 C：前缀自动补全（在 console 侧做容错）**

在 `publicRouter()` 的前缀分流**之前**加一层「裸名归属推断」：若 `envelope.Model` 不匹配任何通道前缀，但**该名字存在于某个已登录通道的目录里**（qoder-proxy 的 26 条裸 id 是最典型来源），则自动补上对应前缀并记录一条 `x-prism-rewritten` 头。

这样 `qwen3.8-flash` 会被正确路由到 qoder，而不是落 core 报 `pinned_account_unavailable`。

**方案 D：至少把错误信息说清楚**

`pinned_account_unavailable` 落到一个「名字不属于 core 任何通道、但属于 qoder 目录」的请求上时，报错应附加提示：*「该模型名属于 qoder 通道，请使用 `qoder-qwen3.8-flash` 形式（或别名 4-max-v1）」*。不改路由行为，只改可诊断性。

### P2 — 其它优化

| 项 | 建议 |
|----|------|
| 上游版本锚定 | `qoder.Dockerfile` 用 `git clone --depth 1`（浮动）。建议 pin 到 tag/commit，避免上游 `main` 变动导致构建结果漂移 |
| 已下架 id 防呆 | 请求已下架/已改名 id 时，上游静默回退不报错。建议 console 侧维护一份「旧 id → 新 id」映射并在 `mergedModels`/`publicRouter` 里做一次归一化 + 响应头提示 |
| 探测结论落盘 | `/admin/probe` 结果 `health present: False`（未落盘到 `probe.go` 的持久层）。进程重启后探测结论丢失，可用性判定回到「未探测」档位。建议核对 `probe.go` 的 `Save` 路径是否被正确调用 |
| `4-max-v1` 说明 | 该别名指向 `qoder-qwen3.8-flash`（非 max）。note 字段写的是「4 千问」，容易让人误以为走的是 max 模型。建议把 note 补全为具体模型名 |

## 十、结论

1. **qoder-proxy 本体无故障**：26/26 模型实测可用，登录/流式/工具/并发/大上下文全通过，版本即上游最新 1.6.0。
2. **「模型无法使用」的直接成因是 console 的发布白名单**：26 个模型只对外公布了 1 个（`qoder-qwen3.8-flash`），而该白名单是**本仓自加**的机制（`f8fed97`/`409997b`），不是上游行为。
3. **次要成因是前缀分流 + core 账号 pin 的叠加误导**：裸名不匹配 `qoder-` 前缀 → 落 core → core 该平台被 pin 且锁定账号不可用 → 报 `pinned_account_unavailable`（错误信息完全不提 Qoder，误导排查方向）。
4. **修复优先级**：P0 扩白名单（配置即可，立即见效）→ P1 加裸名归属推断或改进错误信息 → P2 pin 上游版本、旧 id 防呆、探测落盘核对。
5. **无需改动 qoder-proxy 镜像**；本仓两个补丁在 1.6.0 上仍命中，可继续使用。
