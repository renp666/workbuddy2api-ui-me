## 一、先更正上一轮的一个误判（重要）

上一轮我对 core 的并发扫描得出「9/38 通、23 个 `pinned_account_unavailable`」，**这是错的**——是我自己的扫描方式造成的假象。

`pin.json` 把两个 realm 严格锁定到单个账号（`cn→fd34954f`、`global→725a93fd`）。补丁 0010 的严格锁定语义是：锁定期间该 realm 的请求**只走锁定号**，锁定号「禁用/冷却/熔断/6004 模型冷却/**在途占满**」任一条命中就直接 503，**不换号**。

我的扫描用了 4 并发，而锁定号的在途名额有限——于是绝大多数请求在 **3ms** 内被本地拒掉（`ms=3` 就是「没出网、本地拒」的铁证），只有抢到名额的少数成功。**串行重跑后 core 是 31/38 OK。**

| 扫描方式 | core 结果 | 说明 |
| --- | --- | --- |
| 4 并发 | 8/38 OK | 假象：23 个 `pinned_account_unavailable` 多为在途占满 |
| **串行** | **31/38 OK** | 真实：6 个按设计禁用 + 1 个真失败 |

> 附带结论（值得记一笔）：**严格锁定会把该 realm 的有效并发上限压到「锁定号的在途名额」**。高并发场景下会看到成片 `pinned_account_unavailable`，那不是通道故障，是锁定语义的必然结果。排查时务必串行，别用并发探针。

## 三、三处「不通」的根因与处置

### 3.1 glm / zcode —— 配额耗尽（账号侧，需人工）

**现象**：`glm-*` 11 个模型全失败；别名 `3-strong-v1`（→`glm-5.3`）失败。

**证据**：
- 直接打 `glm-5.3-flash`（该通道唯一被计划授权的模型）返回
  `upstream returned invalid Anthropic message: {"code":1005,"msg":"exceed quota limit"}`
- `/admin/zcode`：`logged_in=true`、`provider=zai`、`plan=start-plan`、`model_filter=plan`、`models=[glm-5.3-flash]`
- 即：账号登录态正常，但 **starter 计划配额已用尽**（`1005 exceed quota limit`），且计划只授权 `glm-5.3-flash` 一个模型（其余模型即便有额度也会因 `3006 model not allowed` 被拒）。

**处置**：账号侧问题，需人工——**续费/升级 z.ai 编码套餐，或换号重新领取**（`7-领取Zcode周末套餐.bat` 仅在周末可用；今天周二）。代码侧无解。

> 附带发现：别名 `3-strong-v1` 指向 `glm-5.3`，而该计划只授权 `glm-5.3-flash`——**即便配额恢复，`3-strong-v1` 仍会因 `3006` 失败**。建议把 `3-strong-v1` 改指 `glm-5.3-flash`（或直接删掉，因为 `3-strong-v2`=core 的 `cn:glm-5.3` 已能覆盖「强模型」位）。此改动会动运行时 `routes.json`，**待确认后再做**。

### 3.2 raccoon —— 凭证过期，刷新被拒（账号侧，需人工）

**现象**：5 个 `raccoon-*` 全失败（`no_healthy_account`）；别名 `2-fast-v2` 失败。

**证据**：
- `runtime/raccoon/state.json`：`{"raccoon-desktop": {"disabled": true, "reason": "token_expired: 刷新被拒，请重新导入凭证"}}`
- 手动刷新返回：`upstream token_expired (http 401): {"code":200003,"message":"authorization_verify_error"}`
- `/admin/raccoon`：`disabled=true`、`points=0`、`has_auth=true`

**处置**：需人工**重新导入桌面端登录凭证**（`~/.box-agent/config/auth.json`）。容器内读不到宿主 DPAPI 登录态，无法自动恢复。代码侧无解。

### 3.3 core `global:deep-model` —— 静态名单里的「幽灵模型」

**现象**：串行扫描中唯一真失败的 core 模型，稳定 3/3 失败。

**证据**（core 容器日志）：
```
WARN: [upstream] chat_stream uid=725a93fd: upstream 400
  {"code":11102,"msg":"model [deep-model] service info not found"}
```

**根因**：`upstream/internal/upstream/global_models.go` 的静态兜底名单 `GlobalModelNames`（21 名）里含 `deep-model`，但**当前上游已不再提供该模型**（`11102 service info not found`）。该静态名单只在「global 模型探测失败」时兜底启用——也就是说，**core 的 global 模型探测此刻是失败/未命中的，退回了含过期条目的静态名单**。

**影响面**：`global:deep-model` **未发布**（公开 `/v1/models` 42 条里没有它），用户正常选不到；但「调用门禁」与「发布白名单」是两套机制，显式传该名仍会命中并 503。属「无害但脏」。

**处置建议**（涉及 core，需走 `patches/` 并评审，本轮未擅改）：
1. 从 `GlobalModelNames` 静态兜底里删掉 `deep-model`（或按探测结果动态收敛）；
2. 顺带排查 global 模型探测为何失败——若探测成功就不会退回过期静态名单。

## 五、`/admin/health`「假绿」的残留形态与建议

上一轮已修「端口活着就报绿」的主形态（commit `01bc129`/`546bff4`：`round.OK` 现在会把 `probe_state=failed` 也算不健康）。本轮复查发现**残留一处**：

`runHealthRound` 只把 `!Reachable || ProbeState=="failed"` 计入不健康。若某通道**从未被探测**（`ProbeState==""`），它既不失败也不翻红——**仍是「假绿」**。实测：trae 在被我手动探测前，`/admin/health` 里 `reachable=true` 却无任何 `probe_state`。

`health.go` 的注释自己就写了「「没测过」与「测了不行」必须区分，不得把未知当健康」，但 `round.OK` 的判定恰恰把「没测过」当成了健康——**文档与实现不一致**。

**建议**（二选一，需确认，本轮未擅改）：
- **A（推荐）**：后台健康轮询里对「无 `probe_state`」的已启用通道跑一次**轻量真调用探测**（每通道 1 个代表模型），让「没测过」不再等于绿；
- **B**：把「已启用且可达但无探测结论」也计为 `round.OK=false`（更严格，但会让新装环境在首轮探测前一直红）。

本轮我已手动把 7 条通道的探测结论补齐（含 trae 76 模型），当前 `/admin/health` 各通道均带 `probe_state`：core ok/3、glm failed、qoder ok/26、opencode ok/5、autoclaw ok/1、**trae ok/72**、raccoon failed。

> trae 探针里 4 个 `timeout@30s`（Doubao-Seed-Code / Evolving / custom_model_1M_text / qwen-3.7-plus）是**瞬时争用**（我同时在跑其他通道探测）：单独计时分别 7.7s / 19.5s / 4.8s / 6.0s，均 <30s；此前 75s 超时的直扫是 76/76 全绿。故**不建议**像 qoder 那样给 trae 单独放宽超时——30s 对 trae 够用，那 4 个是并发放大的偶发。
