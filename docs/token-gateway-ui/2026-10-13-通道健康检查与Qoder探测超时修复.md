## 三、Qoder 通道：数据面全绿，问题在「探测超时」

### 3.1 直名 26/26 全通（只是慢）

逐个 POST `qoder-<id>`，26/26 OK，`served` 全部符合预期；延迟分布：

```text
单发（无并发）：6.4–18.2s
6 路并发    ：11.9–42.6s，其中 8/26 超过 30s（最大 42.6s），但全部成功
```

### 3.2 根因：`probeRequestTimeout = 30s` 比 qoder 真实尾延迟短

- `console/probe.go` 原为单一常量 `probeRequestTimeout = 30 * time.Second`。
- 控制台探测（`probeOne`）与看门狗（`watch.py --timeout 30`）都用它。
- qoder-proxy 每次请求拉起 `qoderclicn` 子进程跑一轮（CLI 代理），天然慢；控制台手工探测按通道并发跑时，qoder 多个模型会越过 30s → 结论写成 `{"category":"timeout","error":"探测超时","durationMs":30001}`。
- 实测证据：`/admin/route` 中 `4-max-v1` 的探测结论 = `ok=false cat=timeout 30001ms 探测超时`，而同一时刻真实调用返回 200 + 正确内容。

**这不是 qoder 坏了，是超时阈值太紧。**

### 3.3 已实施修复（代码）

**`console/probe.go`**：探测超时改为按通道取值，qoder 放宽到 60s，其余通道维持 30s。

```go
var probeChannelTimeouts = map[routeChannel]time.Duration{
	channelQoder: 60 * time.Second,
}
func probeTimeoutFor(c routeChannel) time.Duration { /* 命中则覆盖，否则 30s */ }
```

`probeOne` 改用 `probeTimeoutFor(c)`。这样控制台模型表 / 别名表「一键测试」/ `/admin/probe` 都不再把可用但慢的 qoder 判成超时。

**`scripts/prism-model-watch/watch.py`**：新增 `--qoder-timeout`（默认 60s），对 `realm == "qoder"` 的别名用更宽超时，其余别名维持 `--timeout`（默认 30s）。

### 3.4 验证

- `go vet ./...` 通过；`go test ./...` 通过（新增 `TestProbeTimeoutPerChannel` 锁定「qoder > 默认、其余 == 默认」）。
- `python -m py_compile` 通过；`--help` 可见新参数。
- 看门狗实跑：`4-max-v1` OK；其余 opencode 别名 OK；唯一告警是 `2-fast-v2`（raccoon，与 qoder 无关）。
- 超时口径实测：6 路并发下 qoder 8/26 超过 30s、0/26 超过 60s → 60s 窗口刚好覆盖尾延迟。
